# fs_documents Improvement Plan

## Scope

Create a production-focused cleanup plan for `fs_documents` while respecting these explicit exclusions:

- Do not restrict instructor document/version create/write scope by assigned students/classes.
- Do not mitigate broad company-personnel access to document files or sensitive document content.
- Do not add file-size limits or reduce support for large files/high document volume.
- Do not add renewal approval/review/rejection/pending-verification workflow.
- Do not add multi-company isolation.

## Goals

- Improve install reliability and runtime correctness.
- Fix expiry/dashboard correctness issues.
- Make admin-task document behavior consistent.
- Add server-side business validation that cannot be bypassed through imports/RPC.
- Improve performance through better aggregation and reduced record loading, without limiting capacity.
- Improve maintainability by removing duplicated logic and clarifying entity/document abstractions.
- Add regression tests for critical document workflows.

## Phase 1: Install And Dependency Reliability

1. Add missing dependency on `mail` in `fs_documents/__manifest__.py` because `fs.document` inherits `mail.thread` and `mail.activity.mixin`.
2. Review asset declarations:
   - `document_resizer.js` and `document_view.css` are loaded.
   - `fs_document_list.js`, `fs_document_kanban.js`, and their XML button templates currently appear unused because they are not in `web.assets_backend` and the document views do not specify a custom `js_class`.
3. Choose one asset strategy:
   - Preferred: remove the unused custom list/kanban JS/XML if Odoo XML `<header>` buttons are sufficient.
   - Alternative: wire them properly through assets and `js_class` only if custom controller behavior is still needed.

## Phase 2: Expiry Correctness

1. Replace or supplement stored `expiry_status` so it cannot become stale when the date changes.
2. Recommended approach:
   - Keep `expiry_status` stored only if a scheduled daily recomputation is added.
   - Add a cron that recomputes active documents daily and whenever warning configuration changes.
   - Add a manual server action or helper method for recomputation after upgrades/imports.
3. Add a settings field for `flight_school.document_warning_days` in `res.config.settings` so the warning window is configurable from the UI.
4. Validate `flight_school.document_warning_days` values:
   - Non-negative integer.
   - Safe fallback if the config parameter is invalid or missing.
5. Ensure dashboard counts use current status after recomputation.

## Phase 3: Admin Task Document Model Consistency

1. Add an `admin_task` document entity type in `data/fs_document_entity_type_data.xml`.
2. Update `document_type_admin` so it applies to `admin_task`, not `training_class`. `ADMIN` documents are per-admin-task archive documents: every specific administrative task can have its own archived document/version history.
3. Update the upload wizard:
   - `default_get()` must handle `default_admin_task_id`.
   - Pre-fill `admin_task_id` and its `training_class_id` where useful for display.
   - Allow direct admin-task uploads without requiring users to select a training class first.
   - When launched from a training class, selecting an admin task should create/update the document on that specific `admin_task_id`, not on the class.
4. Update wizard validation:
   - If entity type is `admin_task`, require `admin_task_id`.
   - Ensure `_get_selected_entity_info()` and `_compute_existing_document()` handle direct admin-task context cleanly.
5. Update views:
   - Display `admin_task_id` in entity-specific wizard summaries when direct admin-task upload is used.
   - Ensure the admin-task form upload button opens a fully pre-filled wizard.
6. Update README examples to match the actual method signatures and admin-task workflow.

## Phase 4: Server-Side Business Validation

1. Add a model-level constraint on `fs.document` that validates the selected `document_type_id.applies_to_ids` includes the actual linked entity type.
2. Ensure the constraint covers all supported entity fields:
   - `student_id`
   - `instructor_id`
   - `pilot_id`
   - `training_class_id`
   - `class_type_id`
   - `admin_task_id`
3. Keep the existing “exactly one entity” constraint.
4. Add validation for `has_expiry`:
   - If a document type has expiry, new current versions created through the wizard must have `expiry_date`.
   - For direct `fs.document.version.create()`, decide whether to enforce expiry universally or only in wizard. Recommended: enforce on version create/write when the version is or becomes current.
5. Add issue/expiry consistency validation:
   - If both `issue_date` and `expiry_date` are set, expiry must not be before issue date.
6. Ensure all user-facing validation messages are translatable with `_()`.

## Phase 5: Versioning Correctness And Concurrency

1. Add a SQL uniqueness guarantee for version numbers per document:
   - Unique `(document_id, version_number)`.
2. Add a database-level partial uniqueness guarantee for current versions if supported by Odoo 19 `models.Constraint`, or implement a safe fallback:
   - Preferred DB rule: one `is_current=True` per `document_id`.
   - Fallback: robust ORM write/create logic plus tests.
3. Improve version creation logic:
   - Avoid race-prone `search(order='version_number desc', limit=1)` without locking.
   - If strict DB-level uniqueness is implemented, handle `UniqueViolation` with a user-friendly retry/error pattern.
4. Revisit `current_version_id`:
   - Current implementation computes from `version_ids.filtered('is_current')`.
   - Consider making `current_version_id` explicitly maintained on `fs.document` when versions change to avoid scanning all versions.
5. Ensure changing/restoring current version syncs expiry and related fields exactly once.
6. Prevent archived or deleted versions from accidentally leaving a document with no current version, if deletion remains allowed for managers.

## Phase 6: Performance Improvements Without Capacity Limits

1. Replace repeated dashboard `search_count()` calls with `read_group()` aggregation:
   - One grouped query by `expiry_status`.
   - One grouped query by `related_entity_type` or explicit entity fields.
2. Avoid duplicated dashboard computation:
   - `_compute_summary_kpis()`, `_compute_document_kpis()`, `_compute_entity_kpis()`, and `_compute_doc_graph_data()` currently overlap.
   - Consolidate into shared helper methods that return aggregated counts.
3. Replace `len(record.document_ids)` count computations with grouped counts for batch recordsets:
   - Students
   - Instructors
   - Pilots
   - Training classes
   - Admin tasks
   - Documents/version counts
4. Replace repeated shortcut filtering patterns with a reusable helper per entity model or a shared mixin-like internal method.
5. Avoid decoding entire file payload for size where possible:
   - If Odoo attachment metadata can provide size reliably, use that.
   - If not, defer file-size computation or make it best-effort without forcing large binary decoding during common reads.
6. Keep support for large files and high document volume; optimize queries and computation rather than adding limits.

## Phase 7: Maintainability And Code Quality

1. Introduce centralized entity mapping helpers for `fs.document` and `fs.document.upload.wizard`:
   - Entity code to field name.
   - Entity field to XML ID.
   - Entity field to display label.
   - Entity field to related record.
2. Use those helpers to remove repeated `if student/elif instructor/...` blocks in:
   - `_compute_related_entity_info()`
   - `_check_single_related_entity()`
   - `default_get()`
   - `_onchange_entity_type_id()`
   - `_compute_existing_document()`
   - `_get_selected_entity_info()`
3. Fix outdated public API examples in `README.rst`:
   - Current `get_or_create_for_entity()` signature is `(document_type_id, entity_field, entity_id)`, not `(document_type, entity_model, entity_id)`.
   - Current document type code for medical is `MED`, not `MEDICAL`.
4. Normalize translation usage:
   - Wrap `ValidationError` and `UserError` strings in `_()`.
5. Review whether `auto_install=True` is intentional:
   - If the module should always install when dependencies are installed, keep it.
   - If this is an optional application module, set `auto_install=False`.
6. Decide whether demo data should remain disabled or be updated for test/demo environments.

## Phase 8: User Experience Improvements

1. Make direct admin-task uploads work predictably from the admin-task form.
2. Add clear empty-state guidance for missing expected documents where applicable.
3. Add a “missing documents” smart view/dashboard section if required-document definitions are implemented.
4. Improve upload wizard feedback:
   - Show whether the action creates a new document or adds a new version.
   - Show target entity clearly in every step.
   - Show current existing document/version metadata before adding a new version.
5. Add a post-upload action that returns users to the originating entity when launched from an entity form, or opens the document only when launched from the documents app.
6. Add automatic linking for class-type IP documents:
   - When uploading an `IP` document for a class type, optionally set `reference_document_id` if empty.
   - If multiple IP documents exist, keep manual selection or prompt through a clear list.
7. Improve preview behavior for unsupported file types:
   - Keep download fallback.
   - Show filename, type, and upload metadata.

## Phase 9: Required-Document And Missing-Document Coverage

1. Add a required-document matrix only if this is part of the intended business process.
2. Possible model design:
   - Extend `fs.document.type` with `required_for_entity` or per entity/class-type requirement rules.
   - For class types, define required documents inherited by training classes.
   - For people, define required documents by role/person type.
3. Add computed/actionable missing-document views:
   - Missing student documents.
   - Missing instructor documents.
   - Missing pilot documents.
   - Missing class/class-type/admin-task documents if applicable.
4. Add dashboard cards for missing documents and actions to upload the missing type directly.
5. Do not add approval/renewal states; this remains simple required/uploaded/expired tracking.

## Phase 10: Reminder And Activity Support

1. Add scheduled reminder support for expiring/expired documents if desired.
2. Create mail activities for responsible users or managers, not as an approval workflow.
3. Prevent duplicate activities through a unique key or search-before-create strategy.
4. Add configurable reminder windows, reusing or extending `flight_school.document_warning_days`.

## Phase 11: Tests And Validation

1. Add Odoo tests for core model constraints:

   - Document type must apply to linked entity type.
   - Unique document per type/entity.
   - Issue/expiry date consistency.
2. Add tests for version behavior:
   - First upload creates version 1 and marks it current.
   - Second upload creates version 2 and unsets previous current version.
   - Restoring an older version updates current version and synced expiry.
   - Duplicate current versions cannot occur.
3. Add wizard tests:
   - Student upload.
   - Instructor upload.
   - Pilot upload.
   - Training class upload.
   - Direct admin-task upload.
   - Class-type IP upload.
4. Add expiry tests:
   - Valid, expiring, expired, no-expiry statuses.
   - Cron recomputation changes status when dates pass.
   - Invalid warning config parameter falls back safely.
5. Add dashboard tests:
   - Aggregated counts match created documents.
   - Expired/expiring actions return correct domains.
6. Add install/update validation:
   - Run module update in a test database.
   - Validate all inherited views load.
   - Validate menus/actions open without traceback.

## Decisions And Remaining Clarifications

Resolved decision:

- `ADMIN` documents are true `admin_task` documents. They are an archive for each specific administrative task, not class-level documents optionally linked to a task.

Implementation defaults that do not need to block Phase 1-8 work:

- Enforce expiry for direct `fs.document.version.create()` / `write()` when the related document type has `has_expiry=True` and the version is or becomes current. This prevents imports/RPC from bypassing the wizard requirement.
- Set `auto_install=False` unless there is a confirmed packaging reason to install `fs_documents` automatically whenever `web`, `fs_core`, `fs_people`, and `fs_training` are present. Because this is an application module, manual installation is the safer default.
- Auto-link an uploaded class-type `IP` document to `fs.class.type.reference_document_id` only when the reference is empty. Never overwrite an existing reference automatically.
- If reminder activities are implemented before a more specific routing rule exists, assign them to the flight-school manager group or a configurable manager user/group.

Open business clarifications for optional Phase 9-10 work:

- Should missing-document tracking be implemented now? If yes, provide the mandatory document matrix for each entity type and class/admin-task scenario.
- Should expiring-document reminders go only to managers, or should they also route to responsible instructors/record owners where a responsible user exists?

## Proposed Implementation Order

1. Fix dependency, translations, README/API inaccuracies, and asset cleanup.
2. Fix admin-task entity/model/wizard consistency.
3. Add server-side validation constraints.
4. Fix expiry recomputation and settings UI.
5. Harden version current/number correctness.
6. Refactor aggregation/count performance bottlenecks.
7. Add UX improvements that do not depend on unresolved business rules.
8. Add required-document/reminder features only after the remaining Phase 9-10 business rules are confirmed.
9. Add comprehensive tests and run module update validation.

## Acceptance Criteria

- Module installs/updates cleanly in an Odoo 19 test database.
- Upload wizard works from documents app, student, instructor, pilot, training class, class type, and admin task forms.
- Document type/entity mismatch is rejected server-side.
- Expiry status and dashboard counts stay correct after date changes and config changes.
- Version history has at most one current version per document and no duplicate version number per document.
- Dashboard and document counters use grouped aggregation instead of loading/counting full recordsets in loops.
- Tests cover critical model, wizard, expiry, and versioning behavior.
- Excluded items remain intentionally unchanged.
