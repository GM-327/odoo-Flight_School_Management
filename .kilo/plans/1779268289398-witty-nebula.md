# Prior Experience And Progression Data Plan

## Goal
Improve manual onboarding of organizations that already have flight history, syllabus progress, and training progression data. The implementation should let users enter prior data in detail, apply it safely to person totals and enrollment progression, preserve auditability, and avoid creating fake operational flights or schedules.

## Current-State Findings
- `fs_flights` already has `fs.initial.experience`, but it only stores four aggregate hour fields and applies/reverts directly to person totals. It does not update enrollment hours, syllabus progress, or mission completion.
- `fs_training` already has enrollment hour snapshots in `fs.enrollment.hours` and mission completion in `fs.mission.completion`, but prior data has no source tracking and no dedicated detailed entry flow.
- `fs_flights.fs.flight` distributes completed operational flight hours to people, aircraft, and active student enrollments, but this is for real operations and should not be overloaded for prior manual migration records.
- `fs_people` already stores students, pilots, and instructors as operational personnel roles. No new personnel-history subsystem is needed for this scope.
- `fs_documents` should remain unchanged. Supporting documents can be uploaded later through existing document workflows if needed.
- `fs_scheduling` and `fs_fleet` should mostly remain unchanged. Prior records should not create historical scheduled flights, and aircraft totals should remain operational unless a future explicit requirement says historical records must affect fleet totals.

## Design Direction
Use the existing `fs.initial.experience` model as the prior-experience header and extend it into a controlled manual-entry workflow. Add line-level detail for previous hours and previous syllabus completions. Keep operational `fs.flight` logs separate from prior/manual migration data to prevent double-counting and to keep daily operations clean.

## Scope
- Manual entry only. Do not build CSV/import automation in this pass.
- Support prior experience for students, pilots, and instructors.
- Support previous flight/simulator/solo/instruction hours by source, date range, activity, aircraft type/category, and optional enrollment.
- Support previous syllabus/progression records by enrollment and mission.
- Add tests for apply/revert, progression updates, mission completion updates, and security.

## Module Plan

### `fs_flights`
Primary home for prior-experience entry because it already depends on `fs_training`, `fs_people`, and `fs_fleet`.

Files to change:
- `fs_flights/models/fs_initial_experience.py`
- Add `fs_flights/models/fs_initial_experience_line.py`
- Add `fs_flights/models/fs_prior_syllabus_completion.py`
- Add `fs_flights/models/fs_student_enrollment.py` for enrollment smart buttons/computed counts
- Add optional `fs_flights/models/fs_people_prior_experience.py` to add smart actions to student/pilot/instructor models
- `fs_flights/models/__init__.py`
- `fs_flights/views/fs_initial_experience_views.xml`
- Add `fs_flights/views/fs_student_enrollment_prior_experience_views.xml`
- Add inherited student/pilot/instructor view XML if smart buttons are added
- `fs_flights/views/fs_flights_menus.xml`
- `fs_flights/security/ir.model.access.csv`
- Add tests under `fs_flights/tests/`

Implementation details:
- Extend `fs.initial.experience` with a state workflow: `draft`, `review`, `approved`, `applied`, `cancelled`.
- Keep existing `is_applied`, `applied_date`, and `applied_by` for compatibility with existing records/views, but treat `state` as the new workflow source. Existing applied rows should map to `state='applied'` during upgrade/migration.
- Add source/audit fields: source type, source organization, source reference, date range, verified by/date, company, notes.
- Add computed totals from new line records while preserving legacy aggregate fields during migration.
- Restrict apply/revert to manager/admin-level users. Avoid broad `sudo()`; if elevated writes are needed, keep them to known numeric total fields and enrollment-hour deltas.
- Add `fs.initial.experience.line` for detailed hours. Fields should include header, person link through header, optional enrollment, activity, aircraft type/category, hour kind (`flight`, `simulator`, `solo`, `instruction`), hours, source note, count-toward-enrollment flag, applied enrollment hour link, and applied delta fields.
- Applying a prior-experience record should update person totals and, when an enrollment/activity is provided, update the matching `fs.enrollment.hours` row or create an extra enrollment-hour row. Store exact applied deltas so revert subtracts only what this prior record added.
- Add `fs.prior.syllabus.completion` linked to `fs.initial.experience`, enrollment, mission, completion date, instructor/source organization/reference, notes, and generated `fs.mission.completion`.
- Applying prior syllabus lines should create or update `fs.mission.completion` as completed and preserve source metadata.
- Reverting should only undo mission completions that were created by the prior record, or safely remove source metadata where the completion was not independently changed.
- Rename/menu-label the user-facing area from “Initial Experience” to “Prior Experience” or “Prior Experience & Migration” while keeping XML IDs stable.

### `fs_training`
Add generic source metadata and improve visibility from enrollments without depending on `fs_flights` directly.

Files to change:
- `fs_training/models/fs_mission_completion.py`
- `fs_training/views/fs_mission_completion_views.xml`
- `fs_training/tests/` for mission-source behavior if needed

Implementation details:
- Add source fields to `fs.mission.completion`: source (`manual`, `operational_flight`, `prior_experience`), source organization, source reference, source notes/date, and optional prior flag.
- Keep the existing unique constraint on `(enrollment_id, mission_id)`.
- Extend mission completion list/form/search views to expose source fields and filters.
- Do not add a dependency from `fs_training` to `fs_flights`. Any enrollment UI that references prior-experience models should be implemented as inherited views in `fs_flights`.

### `fs_people`
No new personnel-history model is needed. Existing student, pilot, and instructor models remain the person targets for prior experience records.

Optional view-only integration:
- Add inherited student, pilot, and instructor form smart buttons from `fs_flights` to open related prior-experience records.
- Do not add admin staff history.
- Do not add identity-level historical personnel records.

### `fs_documents`
No changes in this pass. Documents can be uploaded later through existing document workflows if needed.

### `fs_core`
No model changes expected. Reuse existing groups:
- Users: read prior experience/progression records.
- Instructors: may review progress if existing policy allows, but should not approve/apply.
- Managers: create, edit, review, approve, apply.
- Admins: full access including deletion/corrections where safe.

### `fs_scheduling`
No changes expected. Prior migration data should not create scheduled flights or pollute current planning boards.

### `fs_fleet`
No changes expected in this pass. Prior experience may store aircraft type/category for context, but should not alter aircraft totals unless a future explicit requirement asks for historical fleet totals.

## UX Plan
- Replace the simple Initial Experience form with a statusbar form and notebook pages: Summary, Hour Details, Syllabus Progression, Source & Verification, Notes/Audit.
- Add list decorations and filters by state, person type, source type, applied status, and source organization.
- Add smart buttons from student, pilot, instructor, and enrollment forms to related prior-experience/progression records.
- Add an enrollment “Prior Progression” page through an inherited `fs_flights` view showing prior hour lines and prior syllabus completions.
- Keep operational flight entry screens unchanged so users clearly distinguish actual operations from prior records.

## Security And Data Integrity
- Add ACLs for every new model.
- Enforce exactly one person target on `fs.initial.experience` based on `person_type`.
- Enforce non-negative hours and valid date ranges.
- Block edits to applied records except through a controlled revert/correction flow.
- Store exact applied deltas for person totals and enrollment-hour records.
- Avoid creating negative enrollment-hour rows during revert.
- Do not use raw SQL for new logic unless there is a clear performance need. Existing raw SQL in flight distribution should remain untouched unless refactored separately.

## Migration Of Existing Data
- Preserve existing `fs.initial.experience` records.
- For each existing non-zero aggregate hour field, create a corresponding `fs.initial.experience.line` during a module migration script or post-init upgrade step.
- Set new source type to `manual` or `migration` for converted records.
- Map `is_applied=True` to `state='applied'` and preserve `applied_date`/`applied_by`.
- Do not re-apply converted records.

## Test Plan
- `fs_flights`: create prior experience with hour lines; validate constraints; approve/apply; verify student/pilot/instructor totals; verify enrollment hours/progression; revert and confirm only stored deltas are removed.
- `fs_flights`: apply prior syllabus completion and verify `fs.mission.completion` is created/updated with source metadata.
- Security: verify users can read, managers can create/approve/apply, instructors cannot apply, and applied records cannot be edited/deleted by normal users.
- Upgrade: update affected manifests and run module upgrade for `fs_training` and `fs_flights`.

## Acceptance Criteria
- Prior hours can be manually entered in detailed lines and grouped under an auditable source record.
- Applying prior records updates person totals and enrollment progression without creating operational flights.
- Previous syllabus/progression can be recorded and reflected in mission completion.
- Existing initial-experience data remains usable after upgrade.
- Views use Odoo 19 `<list>` and direct XML attributes.
- New models have ACLs and tests.
- Revert/correction logic avoids double-counting and only reverses deltas created by the prior record.
