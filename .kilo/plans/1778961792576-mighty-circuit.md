# fs_core Comprehensive Improvement Plan

## Objective

Improve `fs_core` so it becomes a secure, maintainable, production-ready foundation for the Flight School Management addon suite. The plan addresses reliability, security, performance, technical debt, maintainability, user experience, and missing business-scenario gaps.

## Confirmed Decisions

- Flight School user creation/editing and Flight School role assignment will be Administrator-only.
- Roles and Privileges menus will be restricted to Flight School Administrators.
- The addon suite will be treated as single-company/single-school for now.
- Department codes will be mandatory stable business identifiers.
- Unused seeded rest/daily-hour policy settings will be removed from `fs_core` until implemented elsewhere.

## Current Assessment Summary

`fs_core` is structurally simple and currently performs well, but it has important design gaps:

- Broad ACLs on core Odoo models create security and privilege-escalation risk.
- UI domains restrict menus visually but do not enforce backend security boundaries.
- `fs.department` lacks hierarchy validation, mandatory code rules, stronger identifiers, and search UX.
- Some configuration parameters are seeded but not exposed or consumed.
- Settings are global, which is acceptable for the confirmed single-company/single-school scope but must be documented.
- The module has no dedicated tests.
- Role, privilege, and user-management UX is too close to raw Odoo security models.

## Guiding Principles

- Prefer secure-by-default behavior over permissive convenience.
- Keep changes small and Odoo-native.
- Avoid broad writes to sensitive models such as `res.users`, `res.groups`, and `res.groups.privilege`.
- Make business rules explicit through constraints, controlled workflows, and tests.
- Preserve compatibility for dependent modules unless a breaking change is explicitly accepted.
- Document single-company assumptions clearly instead of adding premature multi-company complexity.

## Phase 1: Security Hardening

### 1.1 Restrict ACLs on sensitive Odoo models

Affected file:

- `fs_core/security/ir.model.access.csv`

Plan:

- Remove manager-level write/create access to `res.users`.
- Remove manager-level write/create access to `res.groups`.
- Remove manager-level write/create access to `res.groups.privilege`.
- Keep user/security administration restricted to `group_flight_school_admin` and/or Odoo system administrators.
- Align ACLs with menu visibility and business intent.

Target access behavior:

- `group_flight_school_user`: read-only access to safe Flight School records only.
- `group_flight_school_manager`: operational access only, without user/security-model administration.
- `group_flight_school_admin`: Flight School user, role, privilege, department, and settings administration.

Risk addressed:

- Prevent Flight School Managers from modifying unrelated users, groups, privileges, or global Odoo security configuration.

### 1.2 Make user and role administration Administrator-only

Affected files:

- `fs_core/views/res_users_views.xml`
- `fs_core/views/menu_views.xml`
- `fs_core/security/ir.model.access.csv`

Plan:

- Keep the simplified Flight School user form only for Administrators.
- Remove any manager path that exposes raw `group_ids` editing.
- Ensure the Users menu is restricted to `group_flight_school_admin`.
- Keep role assignment through standard `group_ids` only in Administrator-only views unless a later workflow requires a dedicated role wizard.

Validation rules:

- Managers cannot create/edit `res.users` through Flight School menus or backend ACLs.
- Managers cannot edit `res.groups` or `res.groups.privilege`.
- Administrators can perform intended user and role administration.

### 1.3 Tighten menu access for Users, Roles, Privileges, and Settings

Affected file:

- `fs_core/views/menu_views.xml`

Plan:

- Restrict `Users`, `Roles`, and `Privileges` menus to `group_flight_school_admin`.
- Decide during implementation whether `General Settings` should remain Manager-accessible or become Administrator-only. The safer default is Administrator-only because it writes global `ir.config_parameter` values.
- Keep Departments access aligned with the final ACL decision. Because Managers currently have department write/create ACLs but the menu is admin-only, either expose it to Managers or reduce Manager ACLs. Recommended default: keep department maintenance Administrator-only unless Managers have a clear operational need.

Risk addressed:

- Avoid exposing security-model configuration and global settings to operational users.

### 1.4 Add server-side access boundaries where useful

Affected files:

- Potential new `security/ir.rule.xml`
- `fs_core/__manifest__.py`

Plan:

- Because the confirmed scope is single-company, do not add company-based record rules now.
- Add record rules only where they enforce a concrete business boundary.
- Do not rely on UI action domains for security-sensitive behavior.
- Prefer stricter ACLs over complex record rules for `res.users`, `res.groups`, and `res.groups.privilege`.

## Phase 2: Department Model Reliability and Business Completeness

### 2.1 Add hierarchy integrity

Affected file:

- `fs_core/models/fs_department.py`

Plan:

- Add recursion prevention for `parent_id` using Odoo hierarchy checks.
- Consider `_parent_store = True` and `parent_path = fields.Char(index=True)` if departments will be used with `child_of` domains, reporting, or large trees.
- Add tests for self-parent and circular-parent rejection.

Risk addressed:

- Prevent invalid department trees that can break hierarchy queries or reporting.

### 2.2 Make department codes required, normalized, and validated

Affected file:

- `fs_core/models/fs_department.py`

Plan:

- Set `code` as required.
- Normalize `code` by trimming whitespace and uppercasing on create/write.
- Keep the unique SQL constraint.
- Add a Python constraint for allowed format.
- Update seed data if needed to comply with the final code format.

Recommended validation:

- Length: 2-12 characters.
- Characters: uppercase letters, numbers, hyphen, underscore.
- No leading or trailing whitespace after normalization.

Risk addressed:

- Prevent duplicate, blank, inconsistent, or invalid department identifiers.

### 2.3 Validate department manager assignment

Affected file:

- `fs_core/models/fs_department.py`

Plan:

- Ensure `manager_id` points to an active internal user.
- Require department managers to belong to a Flight School role if that matches operational policy.
- Do not add company checks because single-company scope is confirmed.

Risk addressed:

- Prevent assigning archived, external, unrelated, or unauthorized users as department managers.

### 2.4 Defer multi-company metadata

Affected file:

- `fs_core/models/fs_department.py`

Plan:

- Do not add `company_id` now.
- Document single-company/single-school scope in `README.rst`.
- Avoid model decisions that would make future company support difficult, such as hard-coding company IDs or assumptions in constraints.

Optional later additions:

- `department_type`
- `base_location` or `home_base`
- `email` or alias/contact fields
- direct user/personnel links if departments become workflow drivers

## Phase 3: Settings and Configuration Cleanup

### 3.1 Remove unused config parameters from fs_core

Affected files:

- `fs_core/data/fs_core_data.xml`
- `fs_core/models/res_config_settings.py`
- `fs_core/views/res_config_settings_views.xml`

Remove from `fs_core` seed data:

- `flight_school.default_timezone`
- `flight_school.minimum_rest_hours`
- `flight_school.max_daily_flight_hours`

Plan:

- Keep only settings that are exposed and used by `fs_core` or dependent modules.
- Remove unused core seed parameters to avoid false configuration surface.
- If scheduling/operations later need rest and daily-hour policies, implement them in the consuming module with validation and tests.

### 3.2 Validate default home base

Affected file:

- `fs_core/models/res_config_settings.py`

Plan:

- Normalize to uppercase and trim whitespace.
- Validate ICAO-like format if the field remains a `Char`.
- Keep the field as `Char` for now unless an airport/base model is introduced later.

Recommended validation:

- Exactly 4 uppercase letters if `Default Home Base` is intended to be an ICAO airport code.

### 3.3 Document global settings scope

Affected files:

- `fs_core/models/res_config_settings.py`
- `fs_core/README.rst`

Plan:

- Keep settings global through `ir.config_parameter` because single-company/single-school scope is confirmed.
- Document that settings are not company-specific.
- Avoid introducing `res.company` extensions at this stage.

## Phase 4: User Experience Improvements

### 4.1 Rename and clarify top-level menu

Affected file:

- `fs_core/views/menu_views.xml`

Plan:

- Rename root menu from `Settings` to `Flight School Settings` unless a broader app-navigation redesign chooses `Flight School`.
- Keep sequence and icon unless there is a separate visual redesign.

Recommended default:

- Use `Flight School Settings` because this module is the configuration foundation.

### 4.2 Improve department views

Affected file:

- `fs_core/views/fs_department_views.xml`

Plan:

- Add a search view.
- Add filters for Active, Archived, Root Departments, With Manager, and Without Manager.
- Add group-bys for Parent Department and Manager.
- Show `active` in the list view.
- Ensure required `code` is visible and prominent in form/list views.
- Consider a hierarchy-friendly UX later if department trees become important.

### 4.3 Improve settings layout

Affected file:

- `fs_core/views/res_config_settings_views.xml`

Plan:

- Organize the current settings under a clearer business section such as Organization Defaults.
- Remove references/comments suggesting unused settings blocks if those settings are removed.
- Add better help text that explains how default home base and default country are consumed by dependent modules.

### 4.4 Simplify user-management UX for Administrators

Affected file:

- `fs_core/views/res_users_views.xml`

Plan:

- Keep simplified user form useful for Flight School Administrators.
- Make the form clearly focused on Flight School account setup.
- Consider adding safe onboarding fields only if needed, such as language/timezone, while avoiding unnecessary duplication of standard Odoo user administration.

## Phase 5: Performance and Scalability

### 5.1 Department hierarchy performance

Affected file:

- `fs_core/models/fs_department.py`

Plan:

- Add `index=True` to fields that are used in searches and filters: `code`, `parent_id`, and `manager_id`.
- Add `_parent_store = True` and `parent_path = fields.Char(index=True)` if hierarchy queries or `child_of` domains are expected.

Recommended default:

- Index `code`, `parent_id`, and `manager_id` when adding search filters.
- Add `_parent_store` if implementing recursive hierarchy checks or hierarchy-heavy UX benefits from it.

### 5.2 Avoid premature complexity

Plan:

- Do not introduce caching, custom SQL, or complex service layers for this module.
- Current performance risk is low; focus on indexes and hierarchy correctness.

## Phase 6: Maintainability and Technical Debt

### 6.1 Clean and standardize docs/comments

Affected files:

- `fs_core/models/fs_department.py`
- `fs_core/models/res_config_settings.py`
- `fs_core/README.rst`
- XML comments in views/security files

Plan:

- Update comments that contradict behavior, especially security group comments.
- Keep docstrings concise and specific to each model.
- Avoid generic generated docstrings that do not explain business intent.
- Document Administrator-only user/role administration.

### 6.2 Confirm generated artifacts are excluded

Current status:

- `.gitignore` already excludes `__pycache__/` and `*.py[cod]`.

Plan:

- No code change required unless artifacts are tracked by git.
- If tracked, remove them from version control during implementation.

### 6.3 Manifest and data ordering

Affected file:

- `fs_core/__manifest__.py`

Plan:

- If new security files are added, load them after groups and before views.
- Keep security files first.
- Keep seed data before views only if views/actions reference the records.
- Remove deleted data files or obsolete references from the manifest if needed.

## Phase 7: Test Coverage

### 7.1 Add `fs_core/tests`

Affected new files:

- `fs_core/tests/__init__.py`
- `fs_core/tests/test_fs_core.py` or split focused test files

Test style:

- Follow existing `TransactionCase` patterns used in `fs_fleet/tests/test_aircraft.py` and `fs_documents/tests/test_fs_documents.py`.

Recommended tests:

- Department code is required.
- Department code is normalized.
- Department code uniqueness is enforced.
- Invalid department code is rejected.
- Department recursion is rejected.
- Department manager validation works.
- Settings persistence works for default home base and default country.
- Invalid default home base is rejected.
- Manager cannot create/edit users through Flight School permissions.
- Manager cannot edit groups or privileges.
- Administrator can perform intended Flight School administration.
- Settings and department views compile during module update.

### 7.2 Add installation/update validation

Plan:

- Run module installation/update tests after implementation.
- Validate that dependent modules still load inherited settings blocks after removing unused core parameters.
- Validate XML views compile.

Suggested commands for implementation phase:

- Odoo module update for `fs_core`.
- Targeted Odoo tests with `--test-tags fs_core` if configured.
- Broader addon-suite tests if security changes affect dependent modules.

## Phase 8: Documentation Updates

Affected file:

- `fs_core/README.rst`

Plan:

- Document the final security model.
- Document that user/role administration is Administrator-only.
- Document role hierarchy.
- Document that settings are global for single-company/single-school deployments.
- Document department code format, required status, uniqueness, and hierarchy rules.
- Document removed unused parameters and where future operational policy settings should live.

## Suggested Implementation Order

1. Update ACL/menu design for Users, Roles, Privileges, and Settings.
2. Remove manager permissions on sensitive core Odoo models.
3. Harden `fs.department` with recursion checks, required code normalization, format validation, indexing, and manager validation.
4. Remove unused seeded config parameters from `fs_core`.
5. Validate default home base.
6. Improve department, settings, and administrator user-management views.
7. Add dedicated `fs_core` tests.
8. Update README and comments.
9. Run module update and targeted tests.
10. Run dependent module smoke tests if ACL/settings changes affect integration points.

## Remaining Clarifications That Can Be Deferred

- Exact root menu label: recommended `Flight School Settings`.
- Exact department code format: recommended 2-12 chars using uppercase letters, numbers, hyphen, and underscore.
- Whether department managers must belong to any Flight School role: recommended yes.
- Whether General Settings should be Administrator-only: recommended yes for global configuration.
- Whether an airport/base model will eventually replace the plain home-base Char field: defer until a base/airport model exists.

## Acceptance Criteria

- Managers cannot modify unrestricted Odoo users, groups, or privileges.
- Users, Roles, and Privileges menus are Administrator-only.
- Department hierarchy cannot contain cycles.
- Department code is required, normalized, validated, unique, and tested.
- Unused `fs_core` config parameters are removed.
- Settings shown in the UI match settings actually stored and consumed.
- Menu visibility matches ACL behavior.
- Single-company/single-school assumptions are documented.
- Dedicated `fs_core` tests cover security, settings, and department integrity.
- Existing dependent modules continue to install/update successfully.
