# Design Plan: Role Transitions in fs_people

## Objective

Add first-class support for role transitions inside `fs_people` so a `fs.student` can become a `fs.pilot`, and a `fs.pilot` can become a `fs.instructor`, without deleting or rewriting historical role records. Historical enrollments, enrollment details, completed and remaining hours, syllabus completion/progression, flights, schedules, documents, qualifications, and role-specific hour totals must remain traceable to the role record that existed when the event happened.

## Current-State Findings

- `fs.person` in `fs_people/models/fs_person.py` is an `AbstractModel`; `fs.student`, `fs.pilot`, and `fs.instructor` are separate concrete tables that copy shared fields through classical inheritance.
- Cross-module records mostly store direct role-specific references, for example `fs.student.enrollment.student_id`, `pilot_id`, `enrolled_instructor_id`, document links, qualification links, and initial-experience links.
- `fs.crew.member` in `fs_scheduling` is a SQL view over active students, pilots, and instructors, using `source_model` and `source_id` plus offset IDs. Existing flight and schedule records store Many2one IDs to that view.
- There are no controllers under the workspace, so role transition support is model, wizard, security, and view work only.

## Design Decision

Use an identity/lifecycle layer plus immutable role records. Do not convert existing student/pilot/instructor rows in place, and do not rewrite historical foreign keys. A transition creates the target role record, links it to the same person identity, marks the source role as former, and records an auditable transition.

This is less risky than refactoring the current abstract `fs.person` into delegated inheritance because the project already has many role-specific references in `fs_training`, `fs_scheduling`, `fs_flights`, and `fs_documents`.

## 1. Database Schema Adjustments

### New `fs.person.identity` Model

Create a concrete identity model in `fs_people` to group all role records that represent the same person.

Recommended fields:

- `name`: display label, usually copied from the current role.
- `active`: standard archive flag for the identity, not for role lifecycle.
- `current_role`: selection with `student`, `pilot`, `instructor`; computed/stored or maintained by transition service.
- `current_student_id`, `current_pilot_id`, `current_instructor_id`: computed Many2one helpers for smart buttons and navigation.
- `student_ids`, `pilot_ids`, `instructor_ids`: One2many role history links.
- `transition_ids`: One2many to role transition records.
- Optional canonical identifiers: `identification_number`, `service_number`, `birth_date`, `nationality_id`. Keep these as identity-level search/display helpers, not as the only source of historical truth.

Access rights:

- Read for normal flight school users.
- Create/write for manager/admin.
- Unlink only for admin or disallowed entirely.

### Add Lifecycle Fields to Role Models

Add the same fields to `fs.student`, `fs.pilot`, and `fs.instructor`.

Recommended fields:

- `person_identity_id`: required Many2one to `fs.person.identity`, `ondelete='restrict'`, indexed, `copy=False`.
- `role_state`: selection `current`, `former`, default `current`, required, indexed, tracking-enabled.
- `role_start_date`: Date, default today, required.
- `role_end_date`: Date, empty while current.
- `transition_in_id`: Many2one to `fs.person.role.transition`, readonly/copy false.
- `transition_out_id`: Many2one to `fs.person.role.transition`, readonly/copy false.
- `is_current_role`: stored computed Boolean for domains: `active and role_state == 'current'`.

Keep the existing role tables as historical snapshots. Do not move shared fields immediately to `fs.person.identity` unless a later refactor is explicitly chosen.

### New `fs.person.role.transition` Model

Add an audit model for lifecycle transitions.

Recommended fields:

- `name`: sequence or computed display, for example `Student -> Pilot: John Doe`.
- `person_identity_id`: required Many2one to identity.
- `transition_type`: selection `student_to_pilot`, `pilot_to_instructor`.
- `transition_date`: Date, required, default today.
- `state`: selection `draft`, `done`, `cancelled`; normal service creates records directly as `done`.
- `from_student_id`, `from_pilot_id`: concrete source links.
- `to_pilot_id`, `to_instructor_id`: concrete target links.
- `source_model`, `source_res_id`, `target_model`, `target_res_id`: optional generic audit fields for reporting.
- `reason`, `notes`: Text/Char.
- `performed_by_id`: default current user.
- `copy_documents`, `copy_qualifications`, `reassign_future_assignments`: Boolean audit flags matching wizard choices.

Use `ondelete='restrict'` on transition links where possible so audit history is not accidentally removed.

### Qualification Traceability

Extend `fs.person.qualification` in `fs_people/models/fs_person_qualification.py` with:

- `origin_qualification_id`: Many2one to `fs.person.qualification`, readonly.
- `transition_id`: Many2one to `fs.person.role.transition`, readonly.

Pilot-to-instructor transition should copy qualification rows instead of moving them. The original pilot qualification remains attached to the former pilot record; the copied instructor qualification is operational for the instructor role and traceable back to the source qualification.

### Crew-Member View Adjustments

Adjust `fs_scheduling/models/fs_crew_member.py` because historical `fs.scheduled.flight` and `fs.flight` rows reference `fs.crew.member` view IDs.

Required changes:

- Add SQL view columns `role_state`, `source_active`, and `crew_selectable`.
- Include former/inactive role records in the view so old Many2one values still resolve in historical forms and reports.
- Compute `crew_selectable` as true only when the source role is active and `role_state = 'current'`.
- Update selection domains in scheduled-flight models, flight wizards, and scheduling wizards to use `[('crew_selectable', '=', True)]`.

This avoids the data-loss symptom where archiving a source role removes the old `fs.crew.member` row and breaks historical crew display.

## 2. Role Transition Logic

### Service Entry Points

Add model methods on source roles:

- `fs.student.action_transfer_to_pilot()`: opens a transition wizard.
- `fs.pilot.action_transfer_to_instructor()`: opens a transition wizard.
- Internal service methods, for example `_transfer_to_pilot(wizard)` and `_transfer_to_instructor(wizard)`, execute the transition atomically.

Add one transient wizard, for example `fs.person.role.transition.wizard`, in `fs_people/wizard/`.

Wizard fields:

- `source_model`, `source_res_id`, `transition_type`, `transition_date`, `reason`.
- Target role inputs required by the target model: pilot license type/number/issue date for Student -> Pilot; instructor department, license details, English fields, capacity defaults, and optional initial availability fields for Pilot -> Instructor.
- Options: `copy_documents`, `copy_qualifications`, `reassign_future_assignments`.

### Student -> Pilot Flow

Within a savepoint:

1. Ensure source is one `fs.student` with `role_state = 'current'`.
2. Ensure or create `person_identity_id` for the source student.
3. Validate the student has no open enrollment in statuses `enrolled` or `active`, unless the wizard explicitly closes/graduates it according to existing training rules.
4. Create a `fs.person.role.transition` draft/audit record.
5. Create a new `fs.pilot` with the same `person_identity_id`.
6. Copy common fields from the student: image, name, identification, gender, birth date, nationality, contact fields, military/rank/service fields, medical fields, user account, active currency, and notes as appropriate.
7. Copy compatible operational fields: security clearance expiry, insurance expiry, advance payment, total flight hours, simulator hours, solo hours, and last flight date.
8. Do not reuse the student license as the pilot license because `fs.student.license_id` is restricted to student-related license types while `fs.pilot.license_id` is restricted to non-student license types. Require target pilot license fields in the wizard.
9. Copy transferable documents only through an optional hook implemented by `fs_documents`; never move the original student documents.
10. Mark the student role as `former`, set `role_end_date`, set `transition_out_id`, and archive the student record if standard lists should hide former students.
11. Mark the pilot role as `current`, set `role_start_date`, set `transition_in_id`.
12. Set identity `current_role = 'pilot'` and return an action opening the new pilot form.

Historical records left untouched:

- `fs.student.enrollment.student_id`.
- All enrollment details, including callsign, status, assigned instructor/aircraft, completed hours, remaining hours, mission/activity completion, syllabus completion, and progression values.
- Completed missions tied through enrollments.
- Historical scheduled/flight crew rows.
- Student documents and initial-experience rows.

### Pilot -> Instructor Flow

Within a savepoint:

1. Ensure source is one `fs.pilot` with `role_state = 'current'`.
2. Ensure or create `person_identity_id` for the source pilot.
3. Validate there is no existing current instructor role for the identity.
4. Check future scheduled/operational assignments where the pilot crew view row is used. If `reassign_future_assignments` is false, block and show a clear error. If true, reassign future rows to the new instructor crew member after creation.
5. Create a `fs.person.role.transition` audit record.
6. Create a new `fs.instructor` with the same `person_identity_id`.
7. Copy common fields from the pilot: image, name, identification, gender, birth date, nationality, contact fields, military/rank/service fields, medical fields, user account, department, callsign, license fields, English fields, total flight hours, simulator hours, solo hours, and last flight date.
8. Initialize instructor-only fields: `max_students`, `max_hours_per_month`, `max_hours_per_3months`, and `total_instruction_hours` from defaults or wizard input.
9. Copy pilot qualifications to instructor qualifications, setting `origin_qualification_id` and `transition_id`. Do not move pilot qualification rows.
10. Copy transferable documents only through an optional `fs_documents` hook; never move the original pilot documents.
11. Mark the pilot role as `former`, set `role_end_date`, set `transition_out_id`, and archive the pilot record if normal lists should hide former pilots.
12. Mark the instructor role as `current`, set `role_start_date`, set `transition_in_id`.
13. Set identity `current_role = 'instructor'` and return an action opening the instructor form.

Historical records left untouched:

- Past pilot enrollments in licensed-personnel classes.
- Past `fs.flight` and `fs.scheduled.flight` crew assignments.
- Pilot documents, initial experience, and qualification rows.

### Hooks for Dependent Modules

Because `fs_people` should not depend on every downstream module, expose extension hooks that other modules can override.

Recommended hooks on the transition service:

- `_prepare_target_role_vals(source, wizard)`.
- `_after_target_role_created(source, target, transition, wizard)`.
- `_copy_transition_documents(source, target, transition, wizard)`: implemented by `fs_documents` if installed.
- `_copy_transition_initial_experience(source, target, transition, wizard)`: implemented by `fs_flights` if needed.
- `_reassign_future_crew_assignments(source, target, transition, wizard)`: implemented/extended by `fs_scheduling` and `fs_flights`.

Use `self.env.get('model.name')` checks for optional models and avoid imports from optional modules inside `fs_people`.

## 3. Validation Mechanisms

### Allowed Transitions

Enforce exactly these transitions at model level:

- `fs.student` -> `fs.pilot`.
- `fs.pilot` -> `fs.instructor`.

Reject reverse transitions and direct Student -> Instructor transitions unless a future requirement explicitly adds them.

### Source Role Validations

Before creating the target role:

- Source record must exist and must not already be `former`.
- Source record must have or be assigned a `person_identity_id`.
- `transition_date` must be on or after `role_start_date`.
- Source must not have an existing `transition_out_id` in `done` state.
- Source must not be archived by a non-transition flow.

### Target Role Validations

Before completing the transition:

- Same identity must not already have a current target role.
- Same identity must not have any other current flight role after the transition completes.
- Required target data must be present, especially pilot/instructor license details when business policy requires them.
- Target role dates must be valid: current roles have no `role_end_date`; former roles have a `role_end_date`.

### Training and Scheduling Validations

Student -> Pilot:

- Block if the student has `fs.student.enrollment` in `enrolled` or `active` status unless the wizard explicitly closes the enrollment through existing graduation/drop logic.
- Do not rewrite existing enrollments. New pilot training should use `pilot_id` on licensed-personnel enrollments.

Pilot -> Instructor:

- Detect future `fs.scheduled.flight` or draft/planned operational records using the source pilot crew member.
- Either block with a `UserError` listing the conflict count or reassign to the new instructor crew row when the wizard option is enabled.
- Never rewrite completed flights; those remain historical pilot activity.

### Data Consistency Constraints

Implement constraints using Odoo 19 patterns:

- Use `models.Constraint` for simple table-level uniqueness/date checks where possible.
- Use Python `@api.constrains` for cross-table checks such as one current flight role per identity.
- Add `models.Index` for frequent filters: `(person_identity_id, role_state)`, `role_start_date`, `role_end_date`, and transition source/target fields.

Recommended checks:

- A role with `role_state = 'current'` must not have `role_end_date`.
- A role with `role_state = 'former'` must have `role_end_date`.
- `role_end_date >= role_start_date` when both are set.
- Only one current role across `fs.student`, `fs.pilot`, and `fs.instructor` for a given identity.
- A transition must have exactly one valid source and exactly one valid target matching `transition_type`.

### Error Handling and Atomicity

- Wrap transition execution in `with self.env.cr.savepoint()` so a failed child copy or validation rolls back the target role and audit updates.
- Raise `UserError` for business blockers that users can fix, such as active enrollments, missing license data, or future assignments.
- Raise `ValidationError` for invariant violations and model constraints.
- Do not use broad `sudo()`. Require manager/admin access for transition actions and only use narrow `sudo()` when linking technical audit records requires it.
- Avoid raw SQL unless needed for concurrency or SQL-view maintenance; parameterize any raw SQL.

## 4. Model, View, Security, and Controller Adjustments

### `fs_people` Models

Update:

- `fs_people/models/__init__.py`: import new identity and transition models.
- `fs_people/models/fs_student.py`: lifecycle fields, transfer action, source validation helpers.
- `fs_people/models/fs_pilot.py`: lifecycle fields, transfer action, source validation helpers.
- `fs_people/models/fs_instructor.py`: lifecycle fields and target validation helpers.
- `fs_people/models/fs_person_qualification.py`: transition trace fields for copied qualifications.
- `fs_people/models/res_users.py`: ensure role transitions copy the existing `user_id` rather than creating duplicate user accounts.

Add:

- `fs_people/models/fs_person_identity.py`.
- `fs_people/models/fs_person_role_transition.py`.
- `fs_people/wizard/fs_person_role_transition_wizard.py`.

### `fs_people` Views

Update form views:

- Student form: add `Transfer as Pilot` button for current students and a status ribbon for former students.
- Pilot form: add `Transfer as Instructor` button for current pilots and a status ribbon for former pilots.
- Pilot/instructor forms: add smart buttons to source/target role and role history.
- Identity form: show current role, all role records, and transition timeline.
- Transition wizard form: collect target role fields and copy/reassignment options.

Update list/search views:

- Default list/search actions show current roles only.
- Add filters for Current, Former, and All Roles.
- History smart buttons use `context={'active_test': False}` so archived source roles remain accessible.

### Security

Update `fs_people/security/ir.model.access.csv`:

- Add ACLs for `fs.person.identity`.
- Add ACLs for `fs.person.role.transition`.
- Add ACLs for transition wizard if needed by Odoo access generation.

Button visibility:

- Restrict transition buttons to `fs_core.group_flight_school_manager` and `fs_core.group_flight_school_admin`.
- Normal users can read role history but cannot execute transitions.

### Dependent Model Adjustments

`fs_scheduling`:

- Update `fs.crew.member` SQL view as described above.
- Add `crew_selectable` domains to crew selection fields in scheduled-flight models and scheduling wizards.
- Ensure historical forms still display former crew rows.

`fs_flights`:

- Add `crew_selectable` domains to add-flight wizard crew fields.
- Keep completed flight crew references unchanged.
- Optional: add a hook to create/apply initial experience on target roles if the project wants cumulative role totals to be explicitly audited outside copied aggregate fields.

`fs_training`:

- Keep existing enrollment foreign keys unchanged.
- Add `active_test=False` contexts where a historical enrollment needs to open a former student/pilot/instructor role.
- No enrollment migration logic is required.

`fs_documents`:

- Keep original document links unchanged.
- Optional extension hook copies only document types applicable to the target role and records origin/transition metadata if those fields are added in that module.

### Controllers

No controller changes are required because no controller files or HTTP routes were found in this workspace.

## Verification Plan

Add Odoo `TransactionCase` tests once implementation starts:

- Student -> Pilot creates a pilot, links same identity, marks student former, and preserves student enrollment details, hours, syllabus completion/progression, and document references.
- Student with an active/enrolled enrollment is blocked unless the wizard explicitly closes it.
- Pilot -> Instructor creates an instructor, copies qualifications, preserves original pilot qualifications, and marks pilot former.
- Duplicate transition attempts are blocked.
- Existing completed flights keep their original crew references and still display crew names through `fs.crew.member`.
- Future assignments are either blocked or reassigned according to wizard option.
- Access rights prevent normal users from executing transitions.

Manual validation:

- Upgrade/install `fs_people`, then dependent modules using the updated `fs.crew.member` view.
- Open student, pilot, and instructor forms and verify current/former filters.
- Execute both transition types from the UI.
- Confirm People dashboard counts current roles only.
- Confirm historical records remain accessible with `active_test=False` contexts.
