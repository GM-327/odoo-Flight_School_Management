# Enhanced Prompt And Plan: Conditional OR Hour Requirements

## Enhanced Implementation Prompt

Implement conditional OR hour requirements in the `fs_training` Odoo 19 module.

Technical context:

- Primary model: `fs.class.type.hours` in `fs_training/models/fs_class_type.py`.
- Existing fields on `fs.class.type.hours`: `class_type_id`, `activity_id`, related `discipline_id`, related `flight_type_id`, and `minimum_hours`.
- Existing uniqueness: `UNIQUE(class_type_id, activity_id)`.
- Parent model: `fs.class.type` has `hour_requirement_ids` and stored computed totals: `total_required_hours`, `total_required_aircraft_hours`, and `total_required_simulator_hours`.
- Existing class type form view edits `hour_requirement_ids` inline in `fs_training/views/fs_class_type_views.xml`.
- Enrollment logic in `fs_training/models/fs_student_enrollment.py` currently creates one `fs.enrollment.hours` line for each `class_type_id.hour_requirement_ids` record and computes progression and remaining hours per mandatory activity.
- Existing enrollment UI in `fs_training/views/fs_student_enrollment_views.xml` presents each required activity as mandatory, so grouped OR alternatives must be displayed clearly to avoid implying every alternative is mandatory.

Business requirement:

- Support required training hours that can be satisfied by alternative activities, such as `MAN-DUAL OR NAV-DUAL` and `VSV-SIM OR IFR-DUAL`.
- Existing ungrouped `fs.class.type.hours` records must remain mandatory AND requirements with unchanged behavior.
- New OR requirements must allow a class type to define one required hour bucket with multiple accepted alternative activities.
- The implementation must avoid double-counting OR alternatives in total required hours, remaining hours, progression, and class type A/C/SIM totals.
- OR groups are satisfied by any combination of logged hours across their alternatives.
- Existing active enrollments must not automatically adopt class type OR-group changes; only enrollments created after the class type change should use the new requirement structure.
- Extra hours must count toward OR group satisfaction when the extra activity matches one of the OR group alternatives.

Recommended data model:

- Add a new persistent model, for example `fs.class.type.hours.group`, to represent an alternative requirement group.
- Add fields on the group model: `class_type_id`, `name`, `sequence`, `operator` with value `any`, `minimum_hours`, explicit `count_as`, and `hour_requirement_ids`.
- Define `count_as` as the explicit total-allocation policy for the group, for example `aircraft`, `simulator`, or `unallocated`. The group always contributes to `total_required_hours`; `count_as` determines whether it also contributes to A/C or SIM totals.
- Add a nullable `requirement_group_id` Many2one on `fs.class.type.hours` pointing to the new group model.
- Keep `activity_id` on `fs.class.type.hours`; each child line is one accepted activity alternative.
- Keep `minimum_hours` on `fs.class.type.hours` for standalone requirements. For grouped OR alternatives, use the group `minimum_hours` as the required bucket total; do not require each alternative line to have its own mandatory minimum.
- Add `hour_requirement_group_ids` One2many on `fs.class.type` for managing groups from the class type form.
- Add enrollment-side snapshot fields or a small enrollment group snapshot model so requirements are evaluated from the enrollment's generated records, not from the mutable current class type template.

OR semantics to implement:

- Use aggregate satisfaction only: the OR group is satisfied when combined logged hours across any accepted alternatives reaches `group.minimum_hours`.
- Document that an OR group represents an interchangeable activity bucket, not a requirement for one alternative activity to individually reach the threshold.
- Do not validate completion of OR conditions when saving `fs.class.type.hours`; that model is a syllabus template and has no student logged hours. Completion validation belongs in enrollment progress/remaining-hour evaluation.

Validation requirements:

- Use Odoo ORM constraints and model methods, not Django-style signals.
- Import `ValidationError` from `odoo.exceptions` if Python constraints are added.
- Validate that every grouped hour requirement has the same `class_type_id` as its group.
- Validate that an OR group has at least two alternative activities before it is considered complete/configurable.
- Validate that group `minimum_hours` is positive.
- Allow the same activity to appear in multiple OR groups for the same class type.
- Replace the current `UNIQUE(class_type_id, activity_id)` SQL constraint because it blocks duplicate activities across groups.
- Add group-aware validation instead: no duplicate standalone activity for the same class type, and no duplicate activity within the same OR group, while allowing the same activity in different groups.

Class type total-hour requirements:

- Update `_compute_required_hour_totals` in `fs.class.type`.
- Standalone lines with no group contribute their own `minimum_hours`.
- Each OR group contributes its `minimum_hours` once.
- For aircraft and simulator totals, standalone lines can use `activity_id.is_sim` as today.
- For OR groups, use the explicit group `count_as` field to allocate totals deterministically, including mixed groups such as `VSV-SIM OR IFR-DUAL`.
- If `count_as = aircraft`, add the group minimum to `total_required_aircraft_hours`; if `count_as = simulator`, add it to `total_required_simulator_hours`; if `count_as = unallocated`, add it only to `total_required_hours`.

Enrollment and progress requirements:

- Add fields on `fs.enrollment.hours` as needed to retain the originating requirement line/group, for example `class_type_hour_id` and `requirement_group_id`.
- Store requirement snapshots on enrollment records at creation time, including standalone minimums, OR group minimums, OR group names, alternative activity membership, and `count_as` where needed.
- Enrollment creation and onchange logic must continue creating mandatory lines for standalone requirements.
- For grouped OR requirements, create activity-level enrollment lines for the accepted alternatives so existing flight posting by activity can still update the correct line.
- Existing enrollments should not be rebuilt automatically when class type templates change. Add an explicit manual rebuild action only if the product requires it later.
- Update progression calculation to evaluate standalone requirements and OR groups separately.
- Standalone progression remains `min(logged, minimum_hours)`.
- OR aggregate progression should be `min(sum(logged across required alternative lines and matching extra-hour lines), group.minimum_hours)`.
- Update remaining-hours calculation so OR groups contribute remaining hours once, not once per alternative line.
- Update the remaining breakdown HTML so it can show text like `Complete 5:00 more in one of: VSV-SIM / IFR-DUAL`.
- Update `_compute_minimum_hours` on `fs.enrollment.hours` so grouped lines do not misleadingly show every alternative as independently required. Prefer adding display/helper fields for group required hours and group label.

View requirements:

- Update `fs_training/views/fs_class_type_views.xml` using Odoo 19 `<list>` views and direct attributes.
- Add UI for managing alternative requirement groups on the class type form, preferably as a separate section under the existing `Hour Requirements` page.
- Keep the existing simple hour requirement list for standalone requirements or clearly mark grouped lines.
- The class type UI must allow users to create a group, set its required hours, select the accepted alternative activities, and choose whether the group counts as A/C, SIM, or unallocated through `count_as`.
- The class type UI must expose the explicit `count_as` selection for every OR group.
- Update `fs_training/views/fs_student_enrollment_views.xml` so grouped OR alternatives are visibly grouped and do not appear as independent mandatory activities.

Security and access:

- If a new persistent group model is added, update `fs_training/security/ir.model.access.csv` with appropriate access rights for the same user groups that can manage class type hour requirements.
- Do not introduce broad `sudo()` usage.

Migration and backward compatibility:

- Existing `fs.class.type.hours` records must remain valid and ungrouped after upgrade.
- New group fields should be nullable so existing data installs and upgrades without conversion.
- A migration is required because the current `UNIQUE(class_type_id, activity_id)` constraint must be removed or replaced to allow the same activity in multiple OR groups for the same class type.
- The migration should drop the old database unique constraint after confirming its actual generated name, then rely on new group-aware Python constraints or compatible SQL constraints.
- Existing rows remain standalone; do not convert existing XML data into groups unless explicit data requirements are added.
- The repository currently has no `fs_training/migrations` directory, so create one only when a real upgrade data change is required.
- Odoo does not need signals for this feature; use constraints, computed fields, onchange logic, and migration scripts if needed.

Testing and validation:

- Add Odoo tests if this module has or can accept a `tests` package. If no tests exist, create minimal TransactionCase coverage for the new requirement evaluator.
- Test that existing standalone requirements behave exactly as before.
- Test that OR groups contribute required totals once.
- Test aircraft/simulator total behavior, especially mixed SIM/A/C OR groups.
- Test enrollment creation for standalone and grouped requirements.
- Test progression and remaining hours for incomplete, partially complete, and complete OR groups.
- Test that matching extra hours count toward OR group satisfaction.
- Test that changing the class type after enrollment does not automatically change existing enrollment requirements.
- Test that the same activity can appear in multiple OR groups for the same class type but not twice in the same OR group.
- Test invalid group configuration, such as one alternative or mismatched class type.
- Validate Python syntax, XML well-formedness, module upgrade, affected views, and access rights.

Deliverables:

- Python model changes in `fs_training/models/fs_class_type.py` and `fs_training/models/fs_student_enrollment.py`.
- XML view changes in `fs_training/views/fs_class_type_views.xml` and `fs_training/views/fs_student_enrollment_views.xml`.
- Security ACL changes if a new model is introduced.
- Migration script to remove/replace the current `UNIQUE(class_type_id, activity_id)` database constraint.
- Optional data XML changes only if specific class type OR groups should be seeded as part of the feature.
- Tests or explicit manual validation notes.

## Execution Plan

1. Implement aggregate-only OR semantics and explicit `count_as` total allocation per the resolved requirements.
2. Add the group model and nullable links while preserving existing standalone hour requirements.
3. Replace the current global activity uniqueness constraint with group-aware validation and the required migration script.
4. Add validations for group consistency, positive required hours, duplicate activities within a group, duplicate standalone activities, and minimum alternative count.
5. Update class type total computations to count standalone lines and OR groups correctly using `count_as`.
6. Update enrollment generation to preserve standalone behavior and add grouped alternative lines plus requirement snapshots.
7. Centralize progression and remaining-hour evaluation around enrollment snapshots, including matching extra-hour credit for OR groups.
8. Update class type and enrollment views so OR groups are editable and understandable in Odoo 19 UI syntax.
9. Add ACLs if a new model is introduced.
10. Add tests for standalone and OR behavior, including mixed aircraft/simulator alternatives, extra-hour credit, duplicate activity policy, and existing-enrollment stability.
11. Validate with syntax checks, XML parsing, and an Odoo module upgrade/install check.

## Resolved Clarifications

- OR group hours are satisfied by any combination of logged hours across the alternatives.
- Mixed SIM/A/C OR groups use an explicit `count_as` field for A/C/SIM total allocation.
- The same activity may appear in multiple OR groups for the same class type.
- Existing active enrollments do not automatically adopt new OR groups; only enrollments created after the class type change use them.
- Extra hours count toward OR group satisfaction when the extra activity matches one of the group alternatives.
