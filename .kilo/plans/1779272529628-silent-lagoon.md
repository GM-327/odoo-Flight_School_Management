# Role-Level and Department ACL Architecture Plan

## Goal

Design a scalable ACL system for the Flight School Odoo 19 suite where effective access is based on two business dimensions:

- hierarchical access level, such as user, instructor, manager, administrator;
- department scope, such as HR, IT, Sales, Operations, Training, Maintenance, or child departments.

The implementation may ignore the current static ACL design. Existing groups, CSV ACLs, and menus should be treated as technical bootstrapping only, not as the final business authorization model.

The target system must let administrators dynamically manage:

- user role-level assignments by department;
- model, record, field, action, button, report, import/export, and delete permissions;
- menu and button visibility at any granularity;
- exceptions and temporary grants;
- audit and compliance review.

## Current Context From Inspection

The current suite contains these custom Odoo modules:

- `fs_core` - central settings, departments, static groups, users, role menus.
- `fs_people` - people, students, instructors, pilots, admin staff, role lifecycle.
- `fs_training` - classes, enrollments, mission completions, training dashboards.
- `fs_fleet` - aircraft, aircraft types/categories, fleet dashboard.
- `fs_scheduling` - scheduled flights, crew SQL view, scheduling wizard.
- `fs_documents` - documents, document versions, upload workflow, document dashboard.
- `fs_flights` - daily operations, simulator operations, flight logs, prior experience.

Useful existing foundations:

- `fs.department` already exists in `fs_core/models/fs_department.py` and supports hierarchy through `_parent_store`, `parent_id`, `parent_path`, and `child_ids`.
- `fs.department.manager_id` points to `res.users`, which can support department manager assignments but should not be the only source of permissions.
- Current Flight School groups are static Odoo groups in `fs_core/security/security_groups.xml`: User, Instructor, Manager, Administrator.
- Current model access is mostly `ir.model.access.csv` rows. No department-specific `ir.rule` layer was found.
- Department fields currently exist on `fs.instructor`, `fs.pilot`, `fs.admin.staff`, and `fs.crew.member`.
- Several important models do not have a direct department field, including students, training classes, enrollments, scheduled flights, actual flights, documents, and aircraft. These need stored security department fields or explicit security classification.
- Menus are currently static XML menus. Some configuration menus are admin-only, but top-level app menus are not consistently group-restricted.
- Several operational methods use `sudo()`. Some are harmless configuration reads, but broad business writes through `sudo()` must be reviewed because they can bypass custom security.

## Design Principles

1. Use Odoo's native ACLs as coarse technical gates only.
2. Keep business authorization in a dedicated Flight School security layer.
3. Treat menu and button visibility as configurable UI policy, not as security.
4. Enforce sensitive decisions server-side in ORM methods and action methods.
5. Prefer stored, indexed fields for department-based filtering.
6. Use deterministic conflict resolution, with explicit deny taking precedence.
7. Make every privilege change auditable.
8. Keep temporary access time-bounded, approved, and revocable.
9. Build the system so a user can have different levels in different departments.
10. Default to least privilege when no rule matches.

## Core Access Control Data Model

### `fs.access.level`

Represents the hierarchy.

Fields:

- `name`
- `code`
- `rank`
- `sequence`
- `active`
- `description`

Recommended level examples:

- rank 10: Viewer
- rank 20: User
- rank 30: Operator
- rank 40: Department Manager
- rank 50: Director
- rank 90: Security Administrator

Rules:

- Higher rank means stronger authority.
- Use `models.Constraint` for unique `code` and unique `rank`.
- Do not hardcode manager/user semantics in code except for seeded defaults.

### `fs.access.role`

Represents business roles mapped to levels.

Fields:

- `name`
- `code`
- `level_id`
- `active`
- `description`
- optional `implied_role_ids`

Notes:

- Business roles should not be the same as Odoo `res.groups`.
- Odoo groups should only grant technical access to the app and security administration screens.
- Administrators can create roles such as HR Manager, Training User, Fleet Auditor, or Scheduling Supervisor without creating new XML groups.

### `fs.access.assignment`

Assigns a role to a user within a department scope.

Fields:

- `user_id`
- `role_id`
- `level_id`, stored related from `role_id.level_id`
- `department_id`
- `include_child_departments`
- `scope`: `own`, `assigned`, `assigned_and_children`, `global`
- `valid_from`
- `valid_to`
- `active`
- `state`: `draft`, `active`, `expired`, `revoked`
- `assignment_type`: `permanent`, `temporary`, `delegated`, `break_glass`
- `assigned_by_id`
- `reason`

Examples:

- User A has User level in HR only.
- User B has Manager level in Training and child departments.
- User C has Viewer level globally for reporting.
- User D has temporary Manager level in Scheduling until a defined expiry date.

### `fs.access.policy`

Central policy for permissions.

Use either one model with a `policy_type` field or separate models for clarity:

- `fs.access.model.policy`
- `fs.access.record.policy`
- `fs.access.field.policy`
- `fs.access.menu.policy`
- `fs.access.button.policy`
- `fs.access.action.policy`
- `fs.access.report.policy`

Shared fields:

- `name`
- `active`
- `policy_type`
- `model_id`
- `operation`
- `effect`: `allow`, `deny`
- `min_level_id`
- `role_id`, optional
- `department_scope`: `none`, `own`, `assigned`, `assigned_and_children`, `global`
- `department_field`
- `custom_domain`
- `field_name`, for field policies
- `menu_id`, for menu policies
- `action_id`, for action policies
- `report_id`, for report policies
- `priority`
- `valid_from`
- `valid_to`
- `reason_required`
- `audit_level`: `none`, `denied_only`, `granted_sensitive`, `all`

Policy guidance:

- Use structured fields for common dimensions instead of encoding everything in domains.
- Use `custom_domain` only for model-specific refinements.
- Keep `department_field` explicit per policy so administrators know which field controls access.
- Sensitive operations such as unlink, export, approve, recalculate, import, and administration should require higher levels than ordinary read/write.

### `fs.access.grant`

Represents temporary or exceptional access.

Fields:

- `user_id`
- `granted_by_id`
- `approved_by_id`
- `model_id`
- `res_id`, optional
- `department_id`, optional
- `operation`
- `level_id`
- `valid_from`
- `valid_to`
- `state`: `active`, `expired`, `revoked`
- `reason`
- `ticket_reference`
- `revoked_by_id`
- `revoked_at`

Rules:

- Never physically delete grants; revoke or expire them.
- Temporary grants should not override explicit deny policies unless a dedicated break-glass policy allows it.
- Record-specific grants should be more specific than model-wide grants.
- Every active temporary grant should appear on an admin review dashboard.

### `fs.access.audit.log`

Append-only audit model.

Fields:

- `event_type`
- `user_id`
- `target_model`
- `target_res_id`
- `operation`
- `decision`
- `policy_id`
- `grant_id`
- `department_id`
- `level_id`
- `reason`
- `ip_address`
- `user_agent`
- `create_date`

Audit these events by default:

- policy create/write/unlink/archive;
- assignment changes;
- temporary grant create/approve/revoke/expire;
- denied access;
- temporary grant usage;
- export/import;
- destructive operations;
- user and security administration changes;
- break-glass usage.

Do not log every ordinary read by default because that will become expensive and noisy.

## Role-Level Mapping

Managers should not have cross-departmental access by default.

Default behavior:

- User level: access own assigned department records only.
- Instructor or operator level: access assigned training/operational records within assigned departments.
- Department manager level: access records in assigned departments and optionally child departments.
- Director level: access multiple configured departments or a functional domain, such as Training plus Scheduling.
- Security administrator level: administer security configuration globally, but should not automatically grant business visibility unless explicitly configured.

Managers can have cross-departmental access only under explicit conditions:

- The manager has an assignment with `scope = global`.
- The manager has assignments to multiple departments.
- The manager is assigned to a parent department with `include_child_departments = True`.
- A temporary grant gives access to another department for a time-bounded reason.
- A policy defines a global operation such as dashboard read-only aggregation.
- A break-glass process grants audited emergency access.

Recommended interpretation of department boundaries:

- Department scope is the primary record boundary.
- A department manager manages only their department unless the assignment includes children.
- Cross-department access must be visible in the user's assignment list and audit trail.
- Configuration/reference records can be global read-only if they do not contain department-sensitive data.
- Shared operational records must define an ownership rule, such as primary department, any participant department, or global operational resource.

## Permission Granularity

Support these operation families:

- Model operations: `read`, `write`, `create`, `unlink`.
- Data movement: `export`, `import`, `print`, `download_attachment`.
- Workflow actions: `confirm`, `approve`, `cancel`, `dispatch`, `complete`, `recalculate`, `archive`, `restore`.
- Field operations: `read_field`, `write_field`, `mask_field`.
- Menu and UI operations: `show_menu`, `open_action`, `show_button`, `show_report`.
- Administrative operations: `manage_policy`, `assign_role`, `grant_temporary_access`, `view_audit`.

Tie each operation to role-department pairs through policies:

- A policy defines the minimum role level needed for an operation.
- The assignment defines where the role level applies.
- The record's security department determines whether the assignment applies to that record.
- Explicit denies can override grants for sensitive models, fields, or states.

Example policy matrix:

| Model Area | Read | Write | Create | Delete | Special |
| --- | --- | --- | --- | --- | --- |
| People | User in department | Manager in department | Manager in department | Admin only | Field masks for personal identifiers |
| Training | User in department | Instructor/manager in department | Manager in department | Admin only | Mission completion requires assigned instructor or manager |
| Fleet | Global read | Fleet manager | Fleet manager | Admin only | Status changes require operations/fleet policy |
| Scheduling | Department read | Scheduler/manager | Scheduler/manager | Admin only | Publish/import/recalculate require explicit action policy |
| Documents | Mirrors linked entity | Instructor/manager for linked entity | Authorized owner/admin | Admin only | File download is separate from metadata read |
| Reports | Aggregated by visible records | No write | No create | No delete | Global dashboards require separate global reporting policy |

### Assignment Workflow

Administrators need tools to:

- select a user;
- assign one or more roles;
- bind each role to a department or global scope;
- include or exclude child departments;
- define validity dates;
- require a reason for elevated access;
- preview effective permissions before activation.

### Policy Workflow

Administrators need tools to:

- choose model, operation, minimum level, and department scope;
- configure field restrictions;
- attach menu/button/action/report visibility to the same policy engine;
- set allow or deny effect;
- define priority and validity dates;
- test policy against a user and sample record;
- publish changes with audit logging.

### Menu and Button Visibility Workflow

Administrators must be able to control menu and button display at any granularity.

Implement `fs.access.menu.policy` and `fs.access.button.policy` with these dimensions:

- `menu_id`
- `button_name` or `button_method`, optional for object buttons
- `view_id`, optional for view-specific buttons
- `action_id`, optional
- `model_id`, optional
- `operation`, normally `show_menu`, `open_action`, or `show_button`
- `min_level_id`
- `department_scope`
- `effect`
- `priority`
- `valid_from` and `valid_to`

Rules:

- UI policies can hide or show root app menus, submenus, reports, actions, object buttons, header buttons, smart buttons, and configuration menus.
- Parent and child visibility must be consistent. If a child menu is visible but the parent is hidden, the UI should either expose the parent path or hide the child.
- Menu changes should clear the relevant web menu cache or require session reload.
- Menu and button visibility must never be treated as enforcement. Direct RPC, direct URL, import/export, and button calls must still pass server-side checks.

### Access Simulator

Add an administrator tool that answers:

- What can this user see?
- Why can this user access this record?
- Which policy denied this operation?
- Which departments are effective for this user?
- Which menus are visible for this user?
- Which buttons are visible for this user?
- Which temporary grants are active?

This tool should be read-only and audit simulator usage on sensitive users.

### Conflict Review

Administrators need a review screen that detects:

- allow and deny rules with same scope;
- menus visible without matching server permissions;
- server permissions without visible menus;
- expired assignments still active because of cache;
- orphan policies pointing to deleted menus or fields;
- broad global policies on sensitive models;
- temporary grants without expiry;
- users with security admin and broad business permissions.

## Enforcement Architecture

### `fs.access.service`

Centralize decisions in one model/service.

Required methods:

- `get_effective_context(user)`
- `can(user, model_name, operation, record=None, field_name=None)`
- `check(user, model_name, operation, record=None, field_name=None)`
- `domain_for(user, model_name, operation)`
- `visible_menus(user, menus)`
- `explain(user, model_name, operation, record=None)`
- `invalidate_security_cache(user_ids=None)`

Evaluation order:

1. Superuser or trusted system context bypass, only where explicitly allowed.
2. Explicit active deny policy or deny grant.
3. Record-specific deny.
4. Record-specific temporary grant.
5. Record policy.
6. Field/action/menu/report policy.
7. Model policy.
8. Default deny.

Tie-breakers:

- Deny beats allow.
- More specific beats less specific.
- Higher priority beats lower priority within the same specificity.
- Record-specific beats model-wide.
- Field-specific write restrictions are checked even if model write is allowed.
- Expired assignments and grants are ignored.

### `fs.access.mixin`

Add a reusable mixin for protected business models.

Model declarations:

```python
_fs_access_control_enabled = True
_fs_access_control_department_field = 'security_department_id'
_fs_access_control_global_model = False
_fs_access_control_sensitive_fields = []
```

Enforcement points:

- `_search` injects read domains.
- `check_access_rule` blocks direct record access.
- `create` checks create permission and validates the target department.
- `write` checks write permission and field-level restrictions.
- `unlink` checks delete permission.
- Custom methods call `fs.access.service.check()` for workflow operations.

Important rule:

- UI visibility, domains, or menu hiding must not be the only control.
- Server-side checks must block unauthorized RPC and direct access.

### Department Resolution

Every protected model must be classified as one of:

- Department-owned: has a stored department field.
- Linked-department: department is derived from a related person, class, flight, or document target.
- Participant-department: visible to users in any participant department.
- Global reference: no department restriction, usually read-only for most users.
- Security-admin-only: configuration or security model.

For scalable domains, add stored indexed fields where possible:

- `security_department_id` for a single owning department.
- `security_department_ids` only if absolutely needed, with a relational strategy that can still be searched efficiently.
- `security_owner_user_id` for user-owned private records.

Avoid non-stored computed department fields for primary read filtering.

## Module Integration

### `fs_core` Integration

Models:

- `fs.department`
- `res.users`
- `res.groups`
- `res.groups.privilege`
- `res.config.settings`

Recommended enforcement:

- `fs.department` is security-critical and should be managed only by security administrators.
- Ordinary users may read active departments needed for display.
- Department manager fields must not automatically create cross-department access. They can seed an assignment, but assignments should be the source of truth.
- `res.users` Flight School administration should move from direct group editing to `fs.access.assignment` management.
- Security administrators should manage policies and assignments through dedicated views, not arbitrary Odoo group editing.

Menu integration:

- Flight School Settings root and all Access Control submenus should be controlled by `fs.access.menu.policy`.
- Existing admin-only menus can remain as technical fallback but dynamic menu policy should determine final visibility.

Conflict behavior:

- If a menu policy exposes user management but the user lacks `manage_security` or `assign_role`, show no menu and deny direct access.
- If a department is archived, assignments tied to it should become inactive or warning-state unless historical access is explicitly allowed.

### User Management Integration

Recommended model changes:

- Add effective security assignment smart button on `res.users`.
- Add computed read-only summaries: effective departments, highest level, active grants.
- Add actions: grant temporary access, revoke assignments, simulate access.

Rules:

- Only security administrators can assign roles, departments, and policy permissions.
- Department managers should not modify their own effective access.
- A user should not grant a role or level higher than their own security administration authority unless using approved break-glass.
- User deactivation must immediately invalidate assignments and active sessions where feasible.

Conflict behavior:

- If Odoo group membership says a user can access an app but dynamic policy denies all menus and records, dynamic policy wins.
- If dynamic policy allows a business operation but the technical Odoo ACL blocks it, the operation fails. Therefore technical ACLs must be broad enough for protected models and narrow for security configuration models.

### `fs_people` Integration

Core records:

- `fs.person`
- `fs.student`
- `fs.instructor`
- `fs.pilot`
- `fs.admin.staff`
- `fs.person.identity`
- `fs.person.role.transition`
- qualifications, licenses, medical classes, ranks

Department strategy:

- `fs.instructor`, `fs.pilot`, and `fs.admin.staff` already have `department_id`; use it as the initial `security_department_id` source.
- `fs.student` lacks direct `department_id`; choose one of these designs:
  - add direct `department_id` if students belong to a department;
  - derive stored `security_department_id` from active enrollment/class;
  - make student visibility participant-based through assigned instructor/class.
- `fs.person` and `fs.person.identity` must be carefully handled because they join multiple role records and historical identities.

Recommended permissions:

- Users can read people in their assigned departments.
- Instructors can update limited student progress fields for students assigned to them.
- Department managers can create/update people in assigned departments.
- Delete/unlink should be admin-only or prohibited in favor of archive.
- Sensitive fields such as identification number, birth date, address, medical/license expiry, and user account linkage should have field policies.

Conflict behavior:

- Role transition workflows must check both source and target department authority.
- If a person transfers department, old department managers should lose normal active-record access but may retain historical transition/audit visibility.
- If a person has multiple active role records in different departments, visibility should be based on any active role department unless a policy restricts by role type.

### `fs_training` Integration

Core records:

- `fs.training.class`
- `fs.student.enrollment`
- `fs.enrollment.hours`
- `fs.mission.completion`
- class types, requirements, flight missions, flight activities, disciplines, admin tasks

Department strategy:

- Add stored `security_department_id` to training classes.
- Enrollment should inherit stored `security_department_id` from the training class, assigned instructor, enrolled pilot/instructor, or student department based on business choice.
- Mission completions and enrollment hours should inherit from enrollment.
- Class types, requirements, flight activities, and mission definitions are global reference/configuration records.

Recommended permissions:

- Users can read training classes and enrollments in their departments.
- Instructors can write progress, mission completion, and enrollment status only for assigned students/classes.
- Department managers can create/update enrollments and classes in their department.
- Administrators can configure class types, requirements, mission templates, and delete/archive sensitive training data.

Conflict behavior:

- If an instructor is assigned to a student from another department, access should be granted through a participant or assignment policy, not automatic global instructor access.
- If an enrollment involves a pilot or instructor in a different department, use participant-department visibility only for read unless write is explicitly granted.
- If module-specific workflow requires completion by assigned instructor, a department manager's generic write policy should not bypass that workflow requirement unless an override action policy exists.

### `fs_fleet` Integration

Core records:

- `fs.aircraft`
- `fs.aircraft.type`
- `fs.aircraft.category`
- `fs.fleet.dashboard`

Department strategy:

- Decide whether aircraft are global resources or department-owned.
- If department-owned, add `security_department_id` to aircraft.
- If shared fleet is global, use global read policies and restricted action policies for state changes.
- Aircraft types and categories should remain global reference data.

Recommended permissions:

- Users can read active aircraft, types, and categories needed for scheduling.
- Fleet users/managers can update aircraft operational fields for assigned fleet departments.
- Delete/unlink aircraft, types, and categories should be admin-only.
- Status transitions such as in-use, maintenance, available, and operational warning updates should be custom action policies.

Conflict behavior:

- Scheduling may need read access to aircraft even if the user lacks fleet management rights. This should be an explicit read policy, not a broad write grant.
- Flight logging may update aircraft status through controlled system-side methods. Those methods must perform explicit action checks or run as trusted service operations with audit.

### `fs_scheduling` Integration

Core records:

- `fs.scheduled.flight`
- `fs.crew.member` SQL view
- scheduling wizard and wizard lines
- routes, pilot functions, cancellation reasons, custom flight types

Department strategy:

- Add stored `security_department_id` to `fs.scheduled.flight` based on training class, primary crew member, assigned instructor, or scheduling department.
- Because `fs.crew.member` is a SQL view and already exposes `department_id`, use it for read filtering and crew selection domains.
- Scheduling wizard records should be restricted by the same department as the generated flights.
- Configuration records such as cancellation reasons and route definitions are global/reference unless business wants department-specific routing.

Recommended permissions:

- Users can read schedules for their departments.
- Scheduling operators can create/write scheduled flights for assigned departments.
- Department managers can approve, cancel, or reschedule within their scope.
- Delete should be admin-only or controlled through cancellation workflow.
- Import/publish/generate schedule actions require action policies.

Conflict behavior:

- If a flight has crew from multiple departments, use participant-department read access, but write authority should default to the owning scheduling department.
- If a user can see a crew member but not the target training class, creation should fail with a clear denial.
- If a menu exposes the scheduling wizard but the user lacks create permission for scheduled flights, the menu should be hidden and the action denied.

### `fs_flights` Integration

Core records:

- `fs.flight`
- daily operations board
- simulator operations board
- initial experience
- prior syllabus completion
- add/cancel/delete/import/recalculate wizards

Department strategy:

- Add stored `security_department_id` to `fs.flight` from the scheduled flight, crew, training class, or operating department.
- Operational boards should use the same security domain as underlying flight records.
- Initial experience and prior syllabus completion should inherit from enrollment/person department.

Recommended permissions:

- Users can read flight logs and operations boards in their departments.
- Operators can create/update operational records where assigned.
- Managers can approve corrections and operational changes in their department.
- Recalculate hours is a sensitive operation and should require explicit `recalculate` action policy.
- Delete should be admin-only and normally replaced by cancel/archive workflows.

Conflict behavior:

- Existing `sudo()` writes for aircraft status, callsigns, person hours, and enrollment hours must be reviewed. Keep only narrowly scoped trusted service operations and audit them.
- If an operational write updates linked records outside the user's department, the service must either deny, require a cross-department grant, or execute as a system update with a logged business justification.
- Wizards must validate target record permissions before performing changes because wizard ACLs alone are not enough.

### `fs_documents` Integration

Core records:

- `fs.document`
- `fs.document.version`
- `fs.document.type`
- document upload wizard
- documents dashboard

Department strategy:

- Documents are polymorphic and must mirror the linked entity's security.
- Add stored `security_department_id` to `fs.document` and `fs.document.version` based on the linked student, instructor, pilot, training class, admin task, or class type.
- For global document types/class types, use global reference policies.
- Separate metadata read from file download.

Recommended permissions:

- Users can read document metadata only for visible linked entities.
- File download should require `download_attachment` or `read_file` policy.
- Instructors/managers can upload/update documents for assigned entities if policy allows.
- Document deletion and version deletion should be admin-only.
- Expiring document dashboard should aggregate only records visible to the user unless a global reporting policy applies.

Conflict behavior:

- If a user can see a student but not the document type, metadata should still avoid leaking restricted file details.
- If a document links to multiple entity fields, constraints should enforce only one owning entity to prevent ambiguous security.
- Document version access must never be broader than parent document access.

### Reporting and Dashboard Integration

Dashboard models:

- people dashboard
- training dashboard
- fleet dashboard
- documents dashboard
- operations boards

Rules:

- Dashboards should use normal ORM searches so record-level domains apply.
- Any dashboard using `sudo()` must be changed or justified as a global aggregate with masking.
- Read-only global aggregates can be allowed by explicit reporting policy.
- Drill-down actions must use the same security domains as the dashboard counts.

Conflict behavior:

- If a user has global dashboard visibility but not record-level visibility, show aggregate totals only and disable drill-down or make drill-down filtered to authorized records.
- If a dashboard menu is visible but all underlying models are denied, hide the menu through menu policy.

## Conflict Resolution With Module Requirements

Effective access is the intersection of:

- technical Odoo ACLs;
- dynamic Flight School policy;
- record department scope;
- module-specific business constraints;
- workflow state restrictions;
- field/action-specific policies.

Rules:

- A policy can restrict module behavior but should not bypass hard business invariants.
- Module-specific requirements win when they are stricter.
- Explicit deny wins over allow.
- Security admin rights do not automatically bypass operational workflow checks.
- Superuser and trusted cron jobs may bypass only through explicit trusted context and audit.

Examples:

- A manager with write access to training records cannot approve a mission completion if the module requires assigned instructor approval, unless a separate `approve_mission_override` policy exists.
- A scheduling operator who can create flights cannot select an aircraft if fleet policy denies aircraft read for that department.
- A user with visible Documents menu cannot download a file without `download_attachment` permission.
- A global reporting user can see aggregate dashboard counts but not necessarily export underlying personal records.

## Edge Cases

### Role Changes

When a user's role changes:

- expire or revoke old assignments instead of deleting them;
- create new assignments with validity dates;
- invalidate security cache immediately;
- audit the changer, old values, new values, reason, and approval;
- re-evaluate visible menus on next request/session reload.

### Department Transfers

When a user or person transfers departments:

- set an effective date;
- preserve historical records in the old department;
- use new department for new active records;
- decide whether old department managers keep read-only historical access;
- update stored `security_department_id` only where the business owner changes;
- audit the transfer.

### Temporary Access Grants

Temporary access should require:

- target user;
- model and operation;
- department or record scope;
- expiry date;
- reason;
- approver for privileged operations.

Maintenance:

- scheduled cron expires grants;
- cache invalidates on grant changes;
- active temporary grants are visible on dashboard;
- grant usage is audited.

### Multi-Department Users

Users can have multiple assignments.

Rules:

- Highest applicable level in a department applies for that department only.
- A global low-level assignment does not raise access inside departments unless policy allows it.
- A high-level assignment in HR does not grant high-level access in IT.
- Deny rules can still block specific models or fields.

### Records Without Department

Classify records explicitly:

- global reference data, readable by users and writable by admins;
- department-owned data, requiring a department before activation;
- user-owned private data;
- system-only data;
- invalid/orphan data needing admin correction.

Default for unclassified records should be deny for non-admin users.

### Archived Users, Departments, and Records

Rules:

- Archived users lose assignments and grants immediately.
- Archived departments cannot receive new assignments unless historical mode is enabled.
- Archived business records remain visible only through historical policies.
- Deactivation should not delete audit logs.

### Imports, Exports, RPC, and Direct URLs

Rules:

- Import requires create/write policies and target department validation.
- Export requires explicit `export` policy, especially for personal or document data.
- Direct RPC and URLs must pass server-side checks.
- Hidden menus do not imply denial unless server policies also deny.

### Scheduled Jobs and System Actions

Rules:

- Cron jobs run as trusted system operations only where necessary.
- Trusted context flags must not be user-controllable.
- System-side updates that bypass user rights must be narrow and audited when they affect sensitive data.

## Performance and Scalability

Recommendations:

- Store effective department ownership in indexed fields.
- Use `fs.department.parent_path` for descendant department queries.
- Cache effective user contexts per user and invalidate on assignment, policy, department, grant, or role changes.
- Avoid `search()` inside loops in security evaluation.
- Batch policy checks where possible.
- Use domains for list filtering rather than post-filtering records in Python.
- Keep audit logging selective to avoid excessive rows.
- Add database indexes on user, role, department, model, operation, validity dates, and state fields.

## Best Practices

### Avoid Privilege Escalation

- Do not let users edit their own assignments or grants.
- Do not let managers grant permissions higher than their own administrative authority.
- Keep `sudo()` out of policy evaluation and business enforcement paths.
- Require explicit approvals for global, delete, export, security-admin, and break-glass permissions.
- Keep security administration separate from operational management.

### Enforce Least Privilege

- Default deny when no policy matches.
- Start users with read-only access to their assigned department.
- Grant write/create/delete/action permissions separately.
- Make delete rare; prefer archive/cancel workflows.
- Treat file download, export, and sensitive fields as separate permissions.

### Audit and Compliance

- Audit every security configuration change.
- Audit denied access and sensitive operation usage.
- Provide periodic reports of global access, temporary grants, dormant users, orphan policies, and menu/policy mismatches.
- Review temporary grants automatically before expiry and after use.
- Keep append-only audit logs protected from ordinary administrators if compliance requires it.

### Secure Menu Customization

- Let administrators manage menu and button display through `fs.access.menu.policy` and `fs.access.button.policy`.
- Support root menus, submenus, actions, reports, and button visibility.
- Always pair menu and button visibility with server-side model/action permissions.
- Run a conflict checker to find menus that expose inaccessible actions.

## Open Design Decisions

These choices should be confirmed before implementation:

- Whether students have a direct department or inherit department from class/enrollment.
- Whether aircraft are global resources or department-owned assets.
- Whether department managers should include child departments by default or only by assignment flag.
- Whether security administrators also receive global business data access, or only security configuration access.
- Whether global dashboards show aggregate-only data or allow drill-down.

Recommended defaults:

- Students inherit department from active class/enrollment unless the business has a stable student department concept.
- Aircraft are globally readable and operationally restricted unless the business tracks owning fleet departments.
- Managers do not include child departments by default unless `include_child_departments` is enabled.
- Security administrators administer security but need explicit business data policies for operational records.
- Global dashboards show aggregate-only data unless drill-down is explicitly granted.

## Success Criteria

- Administrators can define levels, roles, assignments, policies, temporary grants, and menu/button visibility without XML or code changes.
- Managers have no cross-department access unless explicitly assigned, granted, or configured through parent department scope.
- Read, write, create, delete, export, import, field, menu, button, report, and workflow action permissions are independently configurable.
- Users see only authorized menus and records.
- Hidden menus do not create a false sense of security because server-side checks enforce access.
- Temporary grants expire and revoke reliably.
- Explicit deny always wins.
- Module-specific business constraints remain enforceable even when policy grants broad model access.
- Access decisions are explainable and auditable.
- The architecture scales across all Flight School modules without duplicating policy logic in each model.
